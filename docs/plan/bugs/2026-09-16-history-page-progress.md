# 历史分页：加载后淘汰导致请求不前进

日期：2026-09-16。状态：代码路径已确认，修复与回归测试待完成。

分类：程序逻辑、交互体验、架构边界。

`WorldHistoryManager.request` 在执行撤销前，用 `HistoryPageLoadPlan.create` 补齐请求数量。`attachHistoryPage` 合并加载结果，按内存上限裁剪，再用原请求数量调用 `request`。

当请求需要的历史超过内存上限时，裁剪可以移除刚加载的旧记录。下一次请求仍缺少同一记录，于是再次加载。整个过程没有执行撤销，也没有减少剩余数量。

例如，持久历史有五项，每项估算为 70 MiB。每玩家缓存上限为 256 MiB，只能保留三项。请求撤销五项时，第四项加载后被裁剪，下次仍请求第四项。分页上限 64 MiB 不能排除此路径，因为 `WorldHistoryPersistence.loadBatches` 允许每页保留第一个超限条目。

证据位置：

- `WorldHistoryManager.request`：分页判断先于任务创建。
- `WorldHistoryManager.attachHistoryPage`：合并、裁剪、重新请求。
- `HistoryPageLoadPlan.create`：按请求数量减去缓存数量计算缺口。
- `HistoryMemoryCache.trim`：从栈尾移除旧记录。
- `WorldHistoryPersistence.loadBatches`：首项不受剩余分页字节限制。

修复方向：将批量撤销或重做视为一个持有剩余数量的请求，按持久顺序分段加载并执行。每项完成后只计数一次。内存缓存无需同时容纳全部请求历史。分页失败保留可重试状态，不改写未读取的历史目录。

验收要求：用较小的测试缓存预算覆盖跨页执行、加载后淘汰、失败后重试、撤销与重做顺序。必须完成原请求数量，不能通过提高内存上限或减少请求数量规避问题。

实现进展：撤销和重做先执行已缓存条目，缓存耗尽后由原任务请求下一页。任务保留原请求数量和完成计数，等待分页时释放写入租约。分页加载或合并失败会结束当前等待，不在每个 tick 自动重读。

历史相关单元测试通过，新增调度测试覆盖合并失败后的请求保留与显式重试。尚需服务端跨页测试，证明在低缓存预算下完整执行原请求且保持顺序。本项仍未完成验收。

取消修复：初始分页尚未建立世界任务时，取消请求现在也能成功。取消和退出处理会移除待接收页，并取消对应 future。即使读取先完成，只要结果尚未接收，取消后也不会恢复旧操作。
