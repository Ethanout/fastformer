# 2026-09-15 空内容与提交边界

[返回审计索引](D:/重要的资料/项目/__mc/fastformer/docs/plan/bugs/2026-09-15-interaction-performance-update.md)

### BUG-AU（P2，类别 1/2/3）：合法空选区被编码进提交，导致整个工作区被拒绝

- `ClientOperationController.finishDraft` 允许将全空气捕获结果保存为部件，这是可继续编辑的合法状态。
- `submitWorkspace:730-738` 无条件转换全部部件。`OperationWorkspacePlan.Part` 接受空映射，`OperationWorkspacePlanCodec.encode:68-89` 也将其写为空 Blocks 列表。
- 服务端 `OperationWorkspacePlanCodec.decode:113-115` 对空 Blocks 抛出 IOException。即使绕过解码直接调用验证器，`OperationWorkspaceValidator:39` 仍拒绝空部件。因此单个空部件会让同时包含有效内容的整次计划失败。
- 这与 BUG-AJ 共用模型边界问题：编辑部件允许空内容，复制对象和执行计划要求有内容，但调用者没有显式完成两种模型的转换。
- 验证级别：合法状态构造、客户端编码与服务端拒绝的静态链。未做游戏内传输复现。当前修复已委派，尚未验收，不标为已修复。

**修复方案**

1. 客户端建立明确的内容准备边界，忽略没有目标内容且没有源清除内容的部件，仅影响本次执行计划，不从工作区删除空选区。
2. 待删除部件若有非空源快照，必须保留其清除计划。不能只检查目标为空就过滤删除操作。
3. 全部为无变化内容时，在发送前返回无可提交内容的提示，不生成请求和提交锁。混合内容时仅提交实际操作，服务端继续拒绝不合法空部件。
4. 覆盖空与非空混合、全空、空目标但非空待删除源、原部件身份与几何不变。结合 BUG-AJ 验证复制也先处理空结果再构造内容对象。

本轮起用户授权修复，报告保留原审计证据，修复状态与验证结果另行记录。
