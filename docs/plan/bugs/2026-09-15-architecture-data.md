### ARCH-9：客户端编辑历史与服务端历史分离，设置和内存所有权没有统一契约

**BUG-Y（P2，类别 1/2/3/4）：会话历史上限不控制客户端工作区撤回**

- 设置页显示“会话撤回历史”，数值范围为 1 至 800。`FastPlaceSettings.setSessionUndoHistoryLimit:241-244` 保存后，只调用 `OperationManager.updateSessionHistoryLimit`。
- `OperationManager.java:44-48` 只裁剪服务端 `OperationSession`。客户端协议中，该上限仅出现在 `OpenSettingsPayload`，接收后仅传入设置页面，没有更新工作区历史策略。
- 工作区快捷键在 `FastPlaceClientInput.java:331` 调用 `ClientOperationController.undo`，最终使用 `ClientOperationEventStack`。该栈的 `push` 没有数量或内存约束。
- 使用当前生产 `ClientOperationEventStack.java` 编译临时探针，写入 801 个撤回节点后逐一执行，输出 `CLIENT_HISTORY retained=801 executed=801`。这证明实际栈超过设置可表达的最大数量，设置到更小值同样不会影响此栈。未在游戏内点击设置页。
- 因此，“会话内历史记录上限已设为”的反馈没有说明只对服务端旧选区历史生效。若产品本意就是只限制服务端历史，也需要明确标出作用域，不能让工作区撤回暗示受同一上限控制。

**放大成本的结构问题**

- `ClientOperationWorkspace.record` 用闭包持有完整 `Snapshot`。快照包含所有部件引用，直到撤回或清空才释放。持续编辑会保留旧部件和旧方块映射。
- `ClientSelectionPart` 的规范构造函数每次对 `blocks` 与 `sourceSnapshot` 调用 `immutable`。该方法创建新的 `LinkedHashMap`，逐个复制，再执行 `Map.copyOf`。`withTransform` 也走此构造路径，虽未改变方块内容，仍重新复制两张映射。
- 结果是移动、旋转等元数据变化与源方块数量耦合。每次变化都遍历方块映射，完成的编辑又被无界撤回栈持有。此处确认数据复制与保留链，不提供未经测量的毫秒数或内存峰值，不声称每个方块实体内容都会深复制。
- 这不是渲染线程预算能单独解决的问题。即使 ARCH-5 完全异步构网，主线程编辑模型仍有上述分配成本。

**详细修复思路**

1. 先定义历史作用域，区分工作区本地撤回、服务端选区撤回、世界撤回。页面显示各自作用域，设置快照由 ARCH-8 的权威模型同步。若一个设置要同时控制前两者，两个历史实现必须读取同一策略值。
2. 将方块集合封装为不可变源快照对象。只在世界读取、剪贴板解码或实际几何内容变化时复制和验证。移动、旋转、选择和删除标记只新建轻量部件，复用已经验证的源快照，禁止对外暴露可变映射。
3. 历史节点按编辑语义保存前后元数据或增量，持有共享快照引用。一次拖拽只记录一个节点。不要用任意 `Runnable` 隐藏被保留的数据量、作用域和恢复前提。
4. 对历史定义数量策略及独立的内存预算。预算统计唯一共享快照，而不是把每个引用都计为完整副本。裁剪旧节点不能删当前工作区引用的源数据；若支持不限数量，也应采用明确的存储策略并反馈预算限制。
5. 先引入共享快照，再迁移工作区历史节点，最后接通设置同步与即时裁剪。保留现有工作区部件数量规则，不通过偷偷限制部件数量来规避模型成本。

**验收**

- 设置上限为 1、10、800，分别检查工作区和服务端选区的实际可撤回数量。减少上限时裁剪旧节点，页面说明裁剪效果。新建会话、重连和命令修改后策略保持一致。
- 对固定大源做多次移动，检查源快照对象得到复用。实际改变几何内容时旧历史仍可恢复，不能因复用而被后续修改污染。
- 检查拖动中间帧的分配量及编辑结束后的保留内存。性能比较必须使用相同方块数、部件数和编辑次数，不把纯栈探针当成整机性能测试。

### BUG-AC（P2，类别 1/2/3/4）：本地撤回历史为空时，工作区仍消费 Ctrl+Z

- `FastPlaceClientInput.onKey:232-234` 在 `handleWorkspaceShortcut` 返回真后立即结束处理，世界撤回请求位于后面的 249-263 行。
- `WorkspaceKeyboardSemantics.decide` 对工作区撤回只检查路由为 OPERATION 且工作区活动，没有读取本地历史是否为空。
- `handleWorkspaceShortcut:331-337` 调用 `ClientOperationController.undo()` 后无条件返回真，忽略返回值。控制器和工作区在没有撤回节点时实际返回假，因此按键被消费但没有产生撤回，也不会回退到世界请求。
- 这有普通生产入口：接收并捕获服务端选区后，控制器在 249-252 行加入部件并清空历史。此时 `active()` 因工作区非空返回真，本地历史却为空。已有编辑被全部撤回但仍保留初始部件时也会出现相同状态。
- `interaction_rules.md:29` 要求 Ctrl+Z 优先撤回客户端工作区，再请求世界撤回。当前客户端阻止后半段发生。服务端收到请求后仍可按自己的规则先处理选区或任务；本条不承诺下一次请求必然消耗世界历史。
- 提示缺口：此分支没有说明没有本地历史，也没有说明下一层请求被阻止。用户只能看到按键没有效果。

**修复设计**

1. 将命令执行结果区分为已处理、没有可处理步骤、被当前状态阻止。已处理消费按键，没有步骤才进入下一层，被阻止则反馈原因并终止。
2. 不要直接将 `return true` 改为 `return undo()`。当前假值还可能表示正在拖动或提交被锁定，盲目回退会在错误时机触发世界撤回。
3. 在统一撤回路由中依次判断活动手势、本地历史和服务端请求。手势应先结束还是取消，遵守现有撤回语义；明确一次按键最多执行一层动作。
4. 复用 ARCH-9 的历史作用域和 ARCH-7 的手势所有权。输入映射只解析按键，不能另写一套工作区是否可撤回的判断。
5. 验收覆盖刚捕获选区、本地最后一步撤回后、拖动中、等待提交回执、没有工作区但有世界历史，以及服务端没有可撤回记录。检查每次按键的实际目标、请求数量及反馈。

验证级别：当前按键入口、工作区历史和服务端路由的静态完整调用链。未做游戏内按键测试，不将下一层世界撤回结果当作已复现。

### BUG-AI（P2，类别 1/2/4）：移除最后一个部件后，本地删除历史仍在，Ctrl+Z 却绕过本地撤回

- `ClientOperationWorkspace.removeSelectedParts` 在删除前保存快照，删除后记录逆向操作。删除全部部件不会清空历史。剪贴板部件的普通 Delete 也通过编辑事务保留逆向记录。
- `ClientOperationController.active:103-105` 只检查工作区是否非空。`WorkspaceKeyboardSemantics.decide` 对撤回要求工作区活动。因此删除最后一个部件后，即使有本地历史，也拒绝本地撤回命令。
- `FastPlaceClientInput.handleWorkspaceShortcut` 把这个拒绝返回给 `onKey`，后者继续发送 `WorldUndoPayload`。即使服务端选区仍使路由保持 OPERATION，工作区非空条件也会阻止本地调用。
- 最小场景：粘贴一个部件，再按 Delete 移除它，随后按 Ctrl+Z。删除节点在工作区历史中，但快捷键不调用 `workspace.undo()`。Ctrl+A 后用 Ctrl+Delete 移除全部部件也有相同边界。
- 如果没有其他服务端会话或任务且已有世界历史，后续请求可能撤回世界操作。若服务端仍有选区，会先执行其选区撤回。本项确认错误的路由，不把每次按键都描述为必然改变世界。
- `ClientOperationWorkspaceTest.removingSelectedPartsCanBeUndoneAsOneWorkspaceCommand` 删除三个部件中的两个，然后直接调用工作区方法。它既保留非空工作区，也绕过键盘入口，不能覆盖本问题。
- 验证级别：删除历史、活动状态、快捷键策略及后续请求的静态调用链。未运行游戏内按键测试。

**共用修复方案**

1. 与 BUG-AC 合并修复撤回路由。AC 是没有本地历史却消费按键，本项是有本地历史却绕过它。共同原因是把“有可见部件”当成“有本地撤回职责”。
2. 由编辑会话返回撤回能力和阻止原因，分别表示可撤回、没有记录、正在编辑和提交锁定。工作区为空不等于编辑会话及历史已经结束。
3. 让最后一个部件的删除仍能从统一快捷键入口恢复。只有显式结束会话、完成提交或明确清理时才按契约释放本地历史，不能因渲染对象暂时为空就丢失输入归属。
4. 在请求服务端撤回前，完成本地历史的能力判断。不要用创建一个空占位部件来保持活动，也不要直接取消所有空工作区的世界撤回。
5. 验收包括删除唯一部件、删除全部部件、删除剪贴板部件、撤回首次粘贴到空工作区、非空但没有本地历史，以及编辑或提交锁定。断言本地恢复结果和服务端请求次数，不能只直接调用工作区方法。

本轮只记录审计结果，未修改生产代码。

### BUG-AJ（P2，类别 1/2/3）：复制空部件时先抛异常，后置过滤无法返回“没有内容”

- `OperationClipboard.fromWorkspace:26-30` 先用解析结果构造 `Part`，再过滤空内容。但 `Part` 构造器拒绝空 Map，因此过滤之前已经抛出 `IllegalArgumentException`。
- 空部件不是非法工作区状态。`ClientSelectionPart.empty` 显式支持空内容；控制器的 `finishDraft:1044-1051` 将捕获结果直接加入部件，未拒绝全空气选区。`capture` 跳过空气，因此在已有工作区中新建全空气选区即可生成空部件。
- `copySelected:314` 在进入保存用的 try 块之前调用 `fromWorkspace`。快捷键入口也没有转换此异常，因此无法显示已有的“当前没有可复制内容”提示。
- 混合选择也受影响：一个空部件会中断整个收集，非空部件不能按当前过滤意图继续复制。
- 验证级别为当前生产代码的构造器、流执行顺序和输入调用链。没有运行游戏，不将未处理异常直接描述为已复现整个客户端退出。

### BUG-AK（P2，类别 2/3）：提示复制失败时，内存剪贴板已经换成新内容

- `ClientOperationController.copySelected:319-325` 先覆盖 `clipboard` 并设置 `clipboardLoaded=true`，再编码并保存。编码或保存失败仅记录失败提示并返回 false，不恢复原剪贴板。
- `loadClipboard:913-914` 此后直接返回新内存内容。用户看到“复制失败：无法保存剪贴板内容”后，继续粘贴会使用新内容，而不是上次成功复制的内容。
- 对于在替换文件之前发生的保存失败，磁盘仍可能保存旧内容。因此同一客户端内和重启后的粘贴内容可以不同。此条件限定在旧文件保留的失败，不声称所有保存异常都有相同磁盘结果。
- 编码超出方块数量限制也被归为无法保存，且新内存内容已经安装。与 BUG-J 的过晚展开检查有关，但本项关注结果语义和继续粘贴的行为。
- 验证级别为赋值顺序、异常处理、缓存读取及两种语言提示的静态核对。未修改用户剪贴板文件或注入磁盘故障。

**共用修复方案：明确复制结果与保存边界**

1. 将选区内容解析、空内容判定、预算检查、内存发布和持久保存拆为清楚的阶段。先过滤解析后的空 Map，再构造要求非空的剪贴板部件。全部为空时返回明确空结果。
2. 区分全部为空、部分空部件被跳过、解析失败、超过预算和保存失败。不要用一个布尔结果和可变的全局失败键承载全部阶段。返回局部不可变结果，包含已复制数量和保存状态。
3. 明确内存与持久结果的产品规则。推荐保留已成功生成的内存副本，在保存失败时准确提示“已复制，可在本次运行中粘贴，但保存失败”，并提供重试保存。若要求复制整体失败不改变内容，则只有保存成功后才替换当前剪贴板。
4. 预算检查必须在展开与发布之前完成，复用 ARCH-2 的几何成本约束。超限结果不能安装到可直接粘贴的内存剪贴板，再仅通过保存异常表示拒绝。
5. 验收覆盖单个空选区、空与非空混合、全空气捕获、已有旧剪贴板时保存失败、编码超限、当前运行继续粘贴及重启读取。分别断言反馈、内存内容和磁盘内容，不能只检查方法返回 false。

### ARCH-10：预览快照被当成完整世界内容，源引用与目标内容没有分开

**BUG-AA（P1，类别 1/2/3/4）：世界来源箱子的移动目标使用客户端空物品数据**

- 原版区块同步通过 `ClientboundLevelChunkPacketData.BlockEntityInfo.create` 调用 `getUpdateTag`。当前 Minecraft 源码中，`ChestBlockEntity` 及其两个容器父类没有覆盖该方法，继承的 `BlockEntity.getUpdateTag:217-219` 返回空标签。箱子实例的物品列表初始为 27 个空槽。
- 因此，对只通过普通区块同步加载、没有其他模组同步完整物品数据的箱子，客户端方块实体并不持有服务端箱内物品。这里不依赖打开过容器的特殊时序。
- `ClientOperationController.capture:938-967` 却对客户端实体调用 `saveWithFullMetadata`。`ChestBlockEntity.saveAdditional:87-92` 保存的是该客户端实例自己的物品列表，得到可解码但不包含服务器物品的箱子内容。
- `submitWorkspace:731-738` 把这些快照放入 `OperationWorkspacePlan.Part.blocks`。编码与解码保存此内容，没有附带“仅预览数据”的标记或完整性状态。
- 服务端 `ClientWorkspacePlacementTask.composeDesired:228-241` 虽提供了读取世界快照的回调，但 `OperationWorkspaceValidator.validate` 从不调用它。WORLD 部件仅贡献源清除坐标，目标内容沿用客户端快照。现有 `doesNotReadLiveWorldWhenSubmittingSavedWorldSnapshot` 测试还明确要求不调用回调。
- `ClientWorkspacePlacementTask.write` 将客户端目标内容转成 `ReversibleBlockSnapshot`。其 `placeAt` 新建方块实体，并用该标签加载和替换目标实体。写前捕获的服务端完整数据只服务于事务记录和回滚，没有补入移动目标。

**影响与证据边界**

- 最小场景：服务端箱子有物品，客户端通过正常区块加载看到该箱子，选择并移动到空地后提交。上述数据流会生成不含原物品的目标箱子。即使直接提交未变换的世界部件，目标实体替换也需要相同的完整性检查。
- 这是原版同步、模组捕获、编解码、组合和目标加载的静态完整链。尚未在游戏中执行箱子移动，不报告实测物品损失数量，也不声称无法通过世界撤回恢复。正常历史保留的服务端旧快照可能帮助恢复源内容。
- 本条不将所有空 NBT 都当作错误。真正没有方块实体、实体存在但客户端未同步完整数据、完整空容器，是三种不同状态，当前模型无法表达区别。读取异常被转换为 `null` 的路径还会混入第四种状态。
- 当前提示没有说明内容不完整。`validSnapshot` 只检查目标标签能否加载，无法判断物品等字段是否遗漏；目标加载成功也不能证明移动保留了原内容。

**架构修复方案**

1. 分开预览状态、源引用、完整内容和事务旧状态。预览状态只承诺可显示，不能直接成为服务器完整内容。源引用至少包含存档/维度、坐标、快照身份及内容版本。
2. WORLD 移动或复制的完整方块实体数据由服务端源快照提供。若操作语义要求保留选择时内容，先取得有身份的服务端快照并在提交时引用；若语义要求提交时内容，明确读取时点并检测源变化。不能默默在两种语义间切换。
3. 保留“客户端解析形状”的现有原则。客户端仍可提交已解析的目标坐标和变换后方块状态，但增加目标到源的映射，由服务端从源快照填充完整实体内容。无需让服务端重新生成每一种形状。
4. 将实体内容状态建模为“无实体”“完整”“仅预览”“读取失败”，不要用同一个 `null` 表达所有情况。数据不完整时保留工作区，显示需要重新读取源数据或明确选择不保留实体内容，不能默认清空。
5. 剪贴板独立定义导出契约。世界来源复制若要带完整内容，需要在导出时取得完整快照；本地仅有预览时明确标记并在粘贴提交前处理。不要把服务端源引用当作可跨存档永久有效的剪贴板数据。
6. 服务端快照按操作身份管理生命周期，复用 ARCH-1 的事务准入与 ARCH-6 的结果对账。未提交、已提交和等待恢复的数据分别有释放条件及容量预算，避免修复数据来源后引入无界快照缓存。

**迁移与验收**

- 先让当前协议识别不完整实体内容并给出反馈，再增加带身份的服务端源快照与目标来源映射，最后迁移剪贴板。不能只把空标签替换成“当前目标的实体数据”，因为目标可能是另一只箱子。
- 覆盖有物品的单箱、双箱、熔炉进度、带自定义名称的容器、客户端序列化失败、源在选择后改变、目标原本有实体，以及复制到其他存档。
