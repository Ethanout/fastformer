## 架构优先审计与修复方案

本节按更新后的要求归并根因。以下是修复设计，不表示已经修改实现。既有 BUG 条目保留为证据与回归用例；撤回和待验证条目不计为确认缺陷。

### ARCH-1：写入准入分散，锁只识别玩家而不识别事务

**证据与新增 BUG-S（P1，类别 1/4）**

- `ServerInputDispatcher.interactionBlocked:46-49` 检查放置任务、操作任务和历史任务。`BlockTinker.use:68-72` 也检查任务；`QuickReplaceManager.replaceCrosshair:25-28` 却仅检查历史和选区会话，遗漏两类任务。
- `OperationManager.applyWorkspace:410-420` 入队后删除选区会话。此时 `active(player)` 为假，不等于没有任务。`FastPlaceNetwork.handleQuickReplace:215-218` 直接调用快速替换，没有补充任务准入检查。
- 快速替换若在同玩家的操作任务持锁期间到达，可以再次获得该玩家的锁，随后在 `finally` 中释放。`WorldWriteCoordinator.tryAcquire:39-44` 允许同玩家重入，`releaseLease:70-75` 不区分原任务和新请求。
- 当前项目类探针输出 `LEASE original=true replacement=true anotherOwnerAfterReplacement=true`，证明第二次调用释放后，其他玩家能取得原任务尚需的锁。没有启动游戏，未声称已经复现存档损坏。任务下一 tick 会重新申请锁，但两 tick 之间的事务排他性已经失效。
- 触发限定：请求通过其他前置检查，且原任务尚未完成。正常客户端会阻止部分忙碌输入，所以游戏内是否能由状态同步延迟稳定触发仍需实测；服务端方法本身没有维护该不变量。

**目标职责**

- 保留网络处理器只做解码和调度。所有世界写入命令统一进入服务端准入入口，检查设置、恢复状态、玩家任务、目标维度和请求去重。
- 区分 `Session` 与 `Transaction`：前者保存选择和交互状态，后者拥有写入期间的资源。删除选区不得等于结束事务。
- 写入锁返回带服务器生命周期、维度和事务 ID 的租约对象。释放必须匹配租约，不再用玩家 UUID 单独释放。玩家 UUID 仅用于归属、反馈和查找。
- 恢复任务通过显式交接接管原事务租约，不能简单改成“同玩家永不重入”，否则会破坏当前失败恢复交接。
- 快速替换和微调使用短事务适配器，复用准入、前后快照、异常恢复及结果发布。无需为一个方块复制大型任务的全部阶段，但必须遵守同一写入契约。

**迁移与验收**

1. 先为现有入口加入统一准入适配器，保留旧 API 作为委托，避免并行工作区一次改动所有调用点。
2. 引入事务租约并逐个迁移任务、短操作和恢复交接。迁移完成后删除裸 UUID 释放入口，不能长期双轨维护锁状态。
3. 将去重移入连接作用域的请求状态，使用请求 ID 和冻结时仍推进的服务端 tick。清理连接结束状态，覆盖 BUG-P、BUG-Q。
4. 测试提交后会话为空但任务仍在、同玩家新请求、不同玩家竞争、恢复交接、旧租约迟到释放、断线重连和冻结。任何拒绝均产生明确结果，但重复请求反馈需要合并，避免刷屏。

### BUG-W（P1，类别 1/3/4）：小范围方块操作丢弃恢复失败结果，也未接管写入异常

**代码证据与触发条件**

- `BlockTinker.java:243-263` 在写入返回失败或后置快照读取失败时调用 `rollback`。该方法逐个调用 `ReversibleBlockSnapshot.restore`，丢弃返回的布尔值。
- `QuickReplaceManager.java:59-68` 在后置快照读取失败时同样调用 `restore`，但不检查结果。这里不依赖历史记录失败是否可达。
- `ReversibleBlockSnapshot.placeAt` 会在写入失败、方块实体创建或加载失败、最终状态不匹配时返回 `false`。它捕获运行时异常并返回 `false`，所以外层异常日志也不能补上这些被忽略的恢复失败。
- 最小条件序列：写入成功，后置快照读取失败，恢复旧快照也失败。两个入口均返回普通 `false`，释放租约并丢弃局部旧快照。没有将这次操作交给恢复任务，也没有反馈哪些位置尚未恢复。
- 另一个失败分支：`WorldWriteSideEffectGuard.setBlock` 只管理掉落抑制范围，不捕获 `level.setBlock` 的运行时异常。如果方块回调在世界已经发生变更后抛出异常，小操作的 `try/finally` 只释放租约，不执行恢复。不能把释放资源当作恢复世界。

**影响与验证边界**

- 这是代码层面确认的失败处理缺口，触发需要方块写入、序列化或恢复出现异常。没有游戏内故障注入，不声称普通原版方块每次操作都会失败，也不声称已复现存档损坏。
- 恢复失败后，世界可能保留局部新状态，而调用者仅知道操作未成功。`FastPlaceEvents.java:50-58` 还把微调的 `false` 当作继续尝试后续交互的信号，未区分“不适用”和“已尝试但失败”。具体原版交互是否继续取决于后续分支。
- 当前世界任务原则要求恢复状态保留并限制新写入。小操作未复用该恢复契约，与大型任务形成不同的失败语义。该问题独立于 RISK-C 的历史缓存淘汰条件。

**修复设计与验收**

1. 按 ARCH-1 建立短事务执行器，管理旧快照、已经尝试写入的位置、异常和恢复结果。方块类型解析仍留在 `BlockTinker`，不要把微调规则搬入事务层。
2. 将“不适用”“成功”“失败且已恢复”“等待恢复”分成明确结果。事件入口只对“不适用”继续原版交互，失败结果给出可定位的反馈。
3. 检查每个恢复结果。恢复未完成时保留快照并交给既有恢复机制，由它接管租约和后续写入限制。不要释放租约后丢弃唯一的恢复数据。
4. 捕获写入边界的运行时异常并进入同一恢复路径。对异常发生后的未知状态先读取和比对，再按已有恢复契约处理，不能无条件覆盖其他来源的变化。
5. 验收覆盖后置读取失败且恢复成功、恢复连续失败、写入后回调抛异常、两个位置只完成第一个、恢复完成后再次操作。断言失败不会降为普通“不适用”，快照保留到恢复完成，且用户能区分恢复中与已恢复。

本条依据当前生产调用链的静态审计，未运行服务器、未修改生产逻辑。

### ARCH-2：几何、方块状态、成本估算和预览没有统一执行契约

- 证据：BUG-G、BUG-J、BUG-K、BUG-L、BUG-R。`OperationWorkspaceValidator` 自行估算体积，再调用客户端包下的 `WorkspacePreviewComposer`；复制直接展开，渲染另有预算。快速替换预览又独立计算最终状态。
- 包名依赖本身不证明专用服务器崩溃，本节不作此推断。实际问题是同一操作的估算、变换语义和资源限制分散，局部修复容易留下其他路径。

**修复设计**

1. 将纯操作模型移入公共领域模块，不依赖客户端控制器和渲染器。输入包含不可变源快照、变换、重叠规则和模型版本，输出包含变更计划及结构化失败原因。
2. 明确区分最终写入数量、算法扫描体积、临时内存和编码大小。未缩放的稀疏结构不能用包围盒体积冒充写入数量；需要扫描的缩放仍需按扫描成本限流。
3. 让估算与执行使用同一份计划。堆叠使用有界迭代或分块生成，不能先建立全量重复列表再检查限额。未知成本应受运行预算约束，而不是假装估算精确。
4. 分离坐标变换与方块状态变换，并明确空采样、坐标冲突和任意角旋转的规则。直角旋转可使用原版状态规则；不支持的任意角状态不能静默承诺精确朝向。
5. 预览、复制和提交共用规则，但允许不同预算。预览超预算时返回可辨认的降级状态，不影响服务端权威校验；异步结果按源版本及变换版本接收，不能覆盖新操作。

验收采用同一输入跨路径比较：稀疏缩放、空结果、原木轴向、楼梯状态、重复边界和冲突顺序。性能测试分别断言最大单次工作量与峰值保留数据，不能仅断言最终数量正确。

### ARCH-3：历史请求要求先把目标记录装入缓存，缺少独立的进度状态

- 证据：BUG-O 的加载、裁剪和重新请求循环；BUG-D 的分页失败永久忙碌。RISK-C 尚未证明完整生产触发，不作为确定的数据丢失结论。
- `HistoryOrderCatalog` 已经独立保存顺序，应保留此职责。问题不是缺少更多缓存，而是执行进度仍由缓存数量间接决定。

**修复设计**

1. 引入独立历史请求状态，记录请求 ID、方向、剩余数量、当前操作 ID、已完成数量和失败原因。缓存只保存已解码对象，不决定请求是否完成。
2. 从顺序目录取得下一条，加载并固定当前批次，执行和提交后减少剩余数量，再继续下一条。不得要求整次批量请求同时驻留缓存。
3. 页加载必须验证进展：所需 ID 到达、明确缺失或失败，三者必须有其一。空结果和反复淘汰不能自动生成无限的同一请求。
4. 区分临时读取失败、记录损坏、取消与恢复任务。临时失败保留顺序并可重试，结束普通请求的忙碌状态；恢复中的写入保护不能随之解除。
5. 对尚未持久化的批次建立明确所有权：发布完成前由待保存集合固定，或由可恢复日志承担。失败状态按发布批次追踪，不能仅靠最近一个 future 的结果代表全部保存状态。

验收覆盖两条记录总计超过缓存容量、单条超过分页预算、部分成功后失败、取消、重连、损坏页和失败保存期间的淘汰。测试必须断言剩余数量下降或请求明确终止。

### ARCH-4：草稿、连接和读取状态混在生命周期回调中，失败缺少统一结果模型

- 证据：BUG-C、BUG-E、BUG-H、BUG-I。维度切换会结束旧交互并删除草稿；重连等待超时可删除草稿；首次读取失败会被已加载标记阻止重试。
- `ClientSessionManager` 已是状态归属入口，不建议另建一个竞争管理器。应在现有入口内拆开数据身份、连接绑定、读取状态和删除策略。

**修复设计**

1. 持久身份按服务器或存档、玩家和维度划分，连接代次单独管理。断线及维度切换只解绑输入与回调，不隐式销毁另一作用域的数据。
2. 把草稿读取表示为未加载、加载中、就绪、可重试失败、版本不兼容等互斥状态。成功或明确不存在才算加载完成；版本不兼容保留原文件。
3. 删除必须来自明确用户丢弃、已确认提交或规定的保留策略。等待超时只产生“仍待确认”状态，不能证明服务端不再需要草稿。
4. 使用草稿版本和提交 ID 对账，区分提交成功但结果迟到、未提交草稿和新会话。恢复失败不得无条件删除文件，迟到回调不得删除更新的草稿。
5. 操作结果使用稳定原因码和参数，界面负责本地化。至少区分忙碌、超预算、读取失败、版本不兼容、等待确认和无变化。瞬时状态可用行动栏，数据保留与恢复失败应有可回看的提示。

验收覆盖读取失败后重试、版本回退、快照延迟、维度往返、重复结果、旧连接结果和重连后提交对账。中英文键集合相同只验证翻译覆盖，不证明控制流会发出正确提示。

### BUG-AO（P2，类别 2/4）：第二次堆叠的输入单位与实际步距不一致，整体重复基线不明确

- `ClientOperationController.updateTransformGesture` 的方盒 SCALE 分支使用 `WorkspaceSelectionBounds.resolve(part)` 求步长，然后无条件调用 `withRepeatStride`。这个边界包含基线中已有的重复区间。
- 同一分支又在旧重复区间上增加端点。因此第二次手势既增加副本数量，又改变所有副本共用的间距，不是只扩展重复区间。
- 单部件输入阈值却来自 `RepeatDragQuantizer.structureExtent`，它使用原始选区尺寸与 scale，不包含已有重复。由此产生“拖动按源宽度，复制按已展开总宽度”的两个单位。
- 最小例子：源为 x=0、1 两格，其他坐标为 0。第一次向正 X 增加一个副本，结果为 x=0、1、2、3，步长 2。结束手势后再增加一次，步长改为 4，结果为 x=0、1、4、5、8、9。旧副本从 2、3 移到了 4、5。
- 实际项目类探针执行边界、变换、重复区间和内容解析，输出 `REPEAT dragUnit=2 oldStride=2 newStride=4`，最终坐标集合与上述一致。探针按当前控制器的步长和端点表达式组装变换，没有直接调用完整客户端控制器，也未执行游戏输入。
- 原因属于几何模型混用：源单元尺寸、实例间距和当前整体边界没有分开。类似代码还把旋转后的世界包围盒宽度按局部轴名读取，修复时需要结合 BUG-AN 的坐标空间契约，但本项探针只验证未旋转的两次堆叠。

**修复方案**

1. 当前 `current_todo.md` 的 BUG-11 要求按变换后的整体选择框计算步距。不能将步距从 2 变为 4 本身认定为违反设计，原先固定使用原始尺寸的建议撤回。
2. 将当前整体结构保存为本次重复操作的基线，以其 min/max 和明确坐标空间计算本次组间步距。输入量化、预览和提交计划使用同一个步距值。
3. 整体重复保留基线内部相对位置，再创建新的组实例。若意图是修改已有副本间距，必须显式定义这种重排操作，不能与新增整体副本混用。当前探针证明输入单位不一致和旧副本重排，不单凭后者判定产品意图。
4. 公共重复需要固定组成员和组基线。组内已有的相对位置保持不变，组间步长独立于组内每个部件的重复间距。配合 ARCH-2 的共享几何计划，避免渲染和提交分别解释。
5. 验收覆盖连续两次拖动、正负端点、先扩大再缩回、撤回后再拖、旋转后拖动及公共重复。整体复制分支断言基线内部相对位置不变，组间步距与本次整体范围一致，输入阈值与实际间距一致。

本轮只修改审计文档，未改生产逻辑。探针通过表示当前行为得到验证，不表示该行为正确。

草稿英文机械检查为 3.33/100，仅识别 30 个英文词，未通过英文阈值；已人工检查中文表述和证据边界。

### BUG-AM（P2，类别 1/2/4）：旋转手柄与方块内容使用不同中心，含空气选区不能围绕显示中心旋转

- `WorkspaceInteractionResolver.interactionBounds:324-335` 优先使用选区边界，`resolveGizmo` 用其中心建立手柄。`OperationPreviewRenderer` 复用这些边界和手柄。含空气的选区可以有不同于方块占用范围的中心。
- `WorkspacePreviewComposer.resolveValues:46-52` 对每个旋转轴重新从当前占用方块计算中心，不接收选区或手柄中心。`WorkspaceSelectionBounds.rotatedCuboid` 却围绕选区包围盒中心旋转轮廓。
- 输入的 `WorkspaceGizmoDrag` 保存手柄中心来计算拖动角度，但 `ClientOperationController.updateTransformGesture` 只把角度写入变换。单部件没有补偿两个中心的差异。公共旋转又使用占用方块的合并中心，而公共手柄使用选区边界的合并中心。
- 具体例子：方盒范围 x=0 至 4、y=z=0，只有 (0,0,0) 一个非空气方块。显示中心为 (2.5,0.5,0.5)。绕 Y 轴旋转半圈，围绕这个中心的结果应为 (4,0,0)，当前内容解析结果却为 (0,0,0)。
- 本轮实际项目类探针分别调用内容解析器和带指定中心的旋转器，输出 `PIVOT actual=[BlockPos{x=0, y=0, z=0}] aroundShownPivot=[BlockPos{x=4, y=0, z=0}]`。只使用单格字符串值，不加载用户存档，也不涉及方块实体。
- `OperationWorkspaceValidator` 提交时同样调用 `resolveValues(part.blocks(), part.transform())`，因此这个中心选择进入实际目标计划，不只是轮廓画错。未运行游戏内提交，不能把探针视为世界写入验收。

**修复方案：把中心纳入 ARCH-2 的共用几何契约**

1. 明确部件及公共操作的中心规则。若手柄保持选区中心，内容变换必须用该中心；若产品选择占用中心，手柄和轮廓也必须一致。不要由不同消费者自行从不同边界推导。
2. 在手势开始时确定中心，并作为操作几何数据保存。预览、命中、复制和服务端计划使用同一中心及坐标空间。协议与草稿格式需能保持该语义，不能只在客户端临时补偿平移。
3. 多轴旋转使用同一基准和明确的组合顺序。当前每轴从已离散化的结果重算中心，应改为显式几何规则；不能让上一轴的取整结果隐式改变下一轴的旋转中心。
4. 配合 BUG-AL，公共中心在稳定基线上只计算一次。采用选区中心时不需要展开全部重复方块；采用精确占用中心时必须执行预算控制。

### ARCH-11 / BUG-AG（P2，类别 1/2/3/4）：历史忙碌被当作不可取消的故障恢复，普通撤销也失去取消入口

### BUG-Z（P1，类别 1/2/3/4）：玩家换维度事件调用退出，取消应当继续的世界任务

**当前证据**

- `PlayerLifecycleEvents.onPlayerChangedDimension:49-54` 收到玩家换维度事件后调用 `FastPlaceManager.quit(player)`。
- `FastPlaceManager.quit:230-237` 先删除会话。如果玩家尚未处于恢复任务中，则调用放置任务和操作任务的 `cancelTask`，最后显示退出提示。
- 两个 `cancelTask` 都按玩家 UUID 从任务表移除任务，随后调用 `WorldHistoryManager.acceptStoppedTask`。后者在尚无写入时返回 `CANCELLED_BEFORE_WRITE`，已有写入时转入 `startRollback`，不是在原维度继续执行。
- 因此，普通在途任务遇到玩家换维度，会停止原计划并尝试恢复已写部分。此处记录错误的生命周期动作，不声称回滚机制本身失败或写入了错误维度。
- `docs/principles/pseudocode/interaction_spec.md:264-267` 要求换维度不删除会话、选区和工作区，已提交世界任务不因换维度停止。`architecture.md` 同样要求任务保存原始维度并继续运行。当前事件处理与这两条明确要求相反。

**触发与验证边界**

- 提交一个跨多个 tick 执行的任务，在任务完成前通过传送门或维度传送离开。前提是当时没有正在进行的恢复任务，否则 `quit` 的恢复保护分支会跳过任务取消。
- 静态调用链已经确认任务移除和恢复交接。未启动游戏验证传送门时序，不能把已有“维度暂不可用”测试当作本问题的复现。
- `TaskLifecycleGameTests` 的维度可用性场景验证调度器遇到不可用目标维度时保留任务与日志，不经过玩家换维度事件。测试正确覆盖了另一条路径，但不能证明生命周期入口符合要求。
- 用户会收到退出提示，而不是“任务继续在原维度执行”的状态。该问题独立于 BUG-C 的客户端草稿删除；只修客户端仍不能保住服务端任务。

**修复思路**

1. 在 ARCH-4 的生命周期协调层区分“切换运行环境”“用户明确取消”“断线”“服务器停止”。禁止把维度事件直接映射为用户退出命令。
2. 维度切换只解除旧环境的输入、预览和玩家实例引用。编辑会话按规定保留并按维度隔离，当前维度只激活匹配的交互状态，避免坐标缩放后误用旧选区。
3. 世界任务继续由存档、原始维度和任务 ID 持有。向新玩家实例发布原任务进度时明确标出任务维度，结果仍按原提交身份匹配。服务端任务不需要等客户端再次激活原会话。
4. 保留显式取消入口的现有恢复交接，不以删除 `cancelTask` 来掩盖事件路由错误。取消和环境切换分别返回结果，避免两个动作共用同一个“已退出”提示。
5. 新增实际事件级验收：写第一格前换维度、写入中换维度、历史提交中换维度、换回原维度，以及同样阶段的明确取消。前四者必须保留任务，明确取消才进入回滚。并覆盖已有恢复任务的分支，确保不会重复交接。
