# 多部件操作的累计体素预算

日期：2026-09-16。分类：资源成本、交互体验、架构边界。

## 原因

复制和公共旋转原先为每个部件创建独立计数器。每个部件均低于 200000 格，不能证明整个操作低于该限制。复制会保留前面部件的结果，旋转也会同时保留多个部件的解析结果。

## 实现

新增 `CompositionBatch`，为一次操作共用工作量计数器。每个部件成功后，计数器保留其输出格数。后续部件的中间结果与这些已保留结果共同受输出上限约束。

不同部件在同一坐标的格子分别计数，因为调用方保留不同结果映射。无变换的非空输入也计入处理工作量。空输入不消耗额度。发生拒绝后，该批次保持失败状态。

复制与公共旋转均接入此批次。单部件解析继续使用原接口。复制失败仍返回 `TooLarge`，不会把部分结果当作成功剪贴板。

## 验证范围

新增测试覆盖重叠坐标分别计数、累计工作量、失败后的批次状态，以及达到预算后接收空部件。

复制入口测试使用两个各含 110000 格的部件。单独复制成功，共同复制返回输出超限。

本实现限制格数与算法工作量，不是 JVM 字节计量。源快照、值对象大小、单阶段同时存在的临时映射和剪贴板构造副本仍需内存架构审计。服务端跨部件预算也不在本次接线范围内。

定向验证：`gradlew.bat test --tests '*WorkspaceContentPreparerTest' --tests '*WorkspaceCompositionLimitTest' --tests '*GroupRepeatTest' --console=plain` 通过。既有分组点阵测试仍跳过。

性能异常待定位：复制入口测试单项耗时 59.388 秒。该测试包含单部件成功复制和双部件拒绝两次调用。尚不能将耗时归因于某个映射构造，也不能将其等同于单次实际操作耗时。需继续定位，不能据此宣布客户端交互性能达标。
