# 2026-09-15 选择能力与提示归属

### BUG-AQ（P2，类别 1/2/4）：预览降级同时禁用了边框的 Ctrl 选择

- `WorkspacePreviewComposer.resolveForRendering:125-128` 在超出 100,000 方块预算时返回空 Map。合法空选区也返回空 Map，这两种状态没有分别表达。
- `WorkspaceInteractionResolver.resolvePart:175-177` 在使用选区边界之前直接跳过空 Map。`resolveFace:220` 又在 Ctrl 按下时退出。因此未锁定部件即使仍有选区边界，也不提供 Ctrl 边框选择目标。
- `OperationPreviewRenderer:200-238` 使用选区边界继续绘制未锁定部件的边框和标签。绘制可见不代表对应选择入口仍存在。
- 触发：建立含 100,001 个源方块的未变换方盒，按 Ctrl 指向远离中心手柄的边框。相同射线在预算内可得到 Part 目标，超出预算后不能得到该目标。全空气方盒也有此问题。
- 若射线后方有远于原版交互距离的世界方块，`resolveSelectionCreate:245-273` 在 Ctrl 下返回 CreateSelection。输入入口 `FastPlaceClientInput:737-746` 将左键交给 `handleCreateClickInternal:408-413`，清除旧草稿并设置新草稿首点，而不是切换部件选择。这里不声称一次点击已经完成一个新部件。
- 反证：普通面点击仍能选择未锁定方盒，手柄命中仍能追加选择，Ctrl+A 仍可用。本项不是整个部件完全不可操作，也与 BUG-AP 的锁定后不可单独选回不同。
- 验证级别：当前预算分支、提供器优先级、边框绘制和输入处理的静态调用链。没有游戏内点击复现。现有 `WorkspaceInteractionResolverTest.interactionBoundsFallsBackToSelectionWhenPreviewIsOverBudget` 只测边界回退，没有测试最终选择目标。

**修复方案：把选择能力从实体预览预算中分离**

1. 交互解析先读取选区边界与部件能力。标签和边框选择不需要完整展开方块，不应依赖渲染 Map 非空。
2. 预览结果区分空内容、预算降级、失败和就绪。与 ARCH-5 共用结果状态，避免一个空 Map 同时决定画面、选择和新建行为。
3. 与 BUG-AP 共用部件能力模型。保留选择目标并独立判断面编辑、整体变换和提交等待。失败目标的排除规则继续显式检查，不能通过移除空 Map 判断使已拒绝目标重新可编辑。
4. 新建选区仅在确实没有可选择目标时发生。按目标与修饰键统一生成意图，不能因实体预览暂时缺失而改变同一可见边框的含义。
5. 验收覆盖预算边界 100,000/100,001、空方盒、已选和未选部件、Ctrl 追加与取消、射线后方有方块和纯空气。断言选择变化不修改草稿，降级不触发完整体素展开。

### BUG-AR（P2，类别 2/3）：Ctrl 指向已选手柄时提示取消选择，点击却开始变换

- `OperationPreviewRenderer:168-179,198-238` 将部件手柄命中也视为该部件 hovered，并向标签传入 Ctrl 状态。
- `WorkspacePreviewRenderer.renderPartLabel:83-85` 对所有已选且 hovered 的部件显示“Ctrl · 取消选择”，没有区分命中标签、边框还是手柄。
- 实际路由 `FastPlaceClientInput.handleWorkspacePointerClick:1518-1520` 优先处理 Gizmo。`beginWorkspaceGizmoDrag:1545-1557` 只在尚未选中时处理 Ctrl 追加选择，已选部件不会取消选择，而是进入编辑并建立拖动。
- 触发：未锁定且已选中的方盒，按 Ctrl 指向它的移动箭头。标签提示取消选择，点击不会取消，继续拖动还会移动部件。锁定部件不绘制该标签，不将本结论推广到它们。
- 此项确认提示与处理分支不一致，不要求改变 Ctrl 加手柄现有语义。验证为当前绘制与输入调用链，未做游戏窗口验收。

**修复方案：由最终交互意图提供提示**

1. 渲染器不要仅凭 selected、hovered 和 Ctrl 三个布尔值推断动作。最终意图区分切换选择、追加后拖动及已选部件拖动，并提供对应提示。
2. 保留手柄优先级时，手柄命中应显示移动、旋转或缩放提示。只有确实进入 Part 切换分支时才显示取消选择。
3. 标签和准星提示共用同一意图及可用性，避免两处文字给出不同动作。将目前硬编码的中英文标签移入翻译资源，作为这次提示归属修复的一部分。
4. 验收覆盖已选和未选部件、Ctrl 开关、标签、边框、单部件手柄及公共手柄。检查提示所述动作与点击后选择集、编辑状态和几何变化一致。

**排除记录**

面短按的延迟对象在释放时没有应用步数，但当前提示明确要求“长按左键/右键拖动”，现行交互规范也没有要求短按推拉一格。因此本轮不把短按无几何变化登记为确认问题。不能仅依据旧字段名推断现行产品要求。

本轮只记录审计与修复方案，未修改生产逻辑。FastCtx 的读取、查找与检索在本轮恢复正常。

### BUG-AS（P2，类别 2/3）：源方块变化后仍提示可拖动，点击却静默拒绝

- `ClientOperationController.canAdjustAabbFace:543-544` 只检查部件几何能力。`WorkspaceInteractionResolver.resolveFace:237-239` 用此值构造 adjustable 面目标。
- `OperationInteractionIntent.Face.hoverText:100-113` 对该目标显示拖动或推拉提示。目标沿用默认 AVAILABLE，没有源内容变化的原因。
- 真正按下鼠标时，`FastPlaceClientInput.beginWorkspaceFaceDrag:1591-1593` 调用 `sourceSnapshotMatches`。后者重新捕获选区并与保存的方块映射比较。只要映射不同，就返回 false。
- 调用者 `selectOrBeginWorkspaceFace:1625-1627` 忽略启动结果，`handleWorkspacePointerClick:1522-1524` 仍返回已处理。这条拒绝路径没有设置失败提示，也没有刷新部件的源快照状态。
- 触发：创建未变换的世界来源方盒后，其中一个方块被其他玩家改成另一种方块。待客户端接收变化，再从原版交互距离之外指向选区面并拖动。旧部件仍有拖动提示，但启动检查拒绝。再次点击会重新扫描并再次拒绝。
- 边界：拒绝过期源快照本身可以是正确保护。本项问题是没有解释拒绝及恢复入口，不建议直接删除比较或自动覆盖保存内容。若源状态重新与保存快照相同，检查可以重新通过，不声称永久锁死。
- 验证级别：可用性、提示、启动检查和返回值消费的静态调用链。未运行双玩家游戏验收。重新捕获的同步成本归入已有 BUG-F，不重复登记性能问题。

**共用修复方案**

1. 面编辑启动返回明确结果，例如已开始、源内容已变、提交等待或无可编辑目标。输入消费结果与用户反馈分别表达，不能一个 boolean 同时代表两者。
2. 首次发现源变化时显示原因，并提供明确的重新读取或保留旧快照选项。重新读取属于一次可撤回的编辑，不应由 hover 或失败点击自动执行。
3. 将已确认的源版本状态交给部件能力模型。后续提示反映实际状态，不能每次都承诺可拖动后静默拒绝。不要为准确 hover 每帧扫描整个选区。
4. 保留启动时的最新状态检查。缓存“上次可编辑”不能替代真正开始编辑时的检查。与 ARCH-10 的源快照身份共用版本信息，避免再维护一套无作用域的失效标志。
5. 验收覆盖源方块变化、源恢复原样、仅选区外变化、主动重新读取与提交等待。分别检查提示、点击是否被消费、是否建立编辑、源快照是否改变和重复扫描次数。

本节与 BUG-AP、AQ、AR 共用能力、意图和启动结果边界，不建议分别添加三个互不关联的提示变量。

本节草稿英文机械检查两次均为 7.14/100，仅识别 14 个英文词，未通过英文阈值；已人工检查中文说明和证据边界。

### BUG-AT（P2，类别 2/4）：单部件手柄使用整个选择集，作用范围与量化基线分离

- `WorkspaceInteractionResolver:99,125` 明确生成带部件 ID 的单部件手柄和公共手柄。二者共存，单部件手柄以自己的中心及坐标系显示。
- `FastPlaceClientInput.beginWorkspaceGizmoDrag:1545-1575` 点击已经选中的单部件手柄时，不收缩选择集。保存的 baseline 始终为全部 selectedParts。后续 `updateTransformGesture` 不接收目标部件 ID，只遍历完整 baseline。
- 生产类探针选择 A、B，激活 A，采用与单部件入口相同的 baseline，并以 common=false 调用 MOVE。实际输出为 `PART_GIZMO common=false first=(1.0, 0.0, 0.0) second=(1.0, 0.0, 0.0)`。B 同样发生位移。
- 对宽度分别为 4 和 2 的 A、B，单部件 SCALE 输出 `PART_STACK firstStride=4 secondStride=2`。输入量化却在 `workspaceRepeatUnit:2068-2076` 只读取命中的那个部件。因此一套拖动单位驱动不同部件各自的重复步距，不是公共组步距。
- 混合方盒与棱柱时，这个范围问题更明显：公共手柄因 includesPrism 不提供 SCALE，但单部件手柄仍提供 SCALE。单部件入口保存全部选中部件，`workspaceScaleUsesRepeat` 又因任意棱柱而切到一格单位；控制器对棱柱改尺寸、对方盒增加重复。此混合路径为静态核对，探针没有构造棱柱。
- 设计依据：`interaction_rules.md:25` 规定普通点击只选中一个部件，Ctrl 点击追加或取消；第 28 行区分部件中心和公共中心。现有规则没有明确规定“点击已选部件手柄可对全部部件执行各自变换”的例外。
- 证据边界：已确认作用范围和量化规则的实现差异。若产品有意支持选中部件分别变换，应将其定义为第三种明确模式，并提供对应反馈；不能只依据 common=false 的名称断言任何多部件变换都错误。
- 探针使用当前生产控制器和空内容的合法方盒模型，不访问游戏存档。取消后的断言通过，输出 `CANCEL restoresBoth=true`。它证明控制器更新范围与取消恢复，不等于完成游戏鼠标命中验收。

**修复方案：把作用范围放入手势计划**

1. 手势开始时固定目标集合、作用模式、中心、轴空间和量化单位。作用模式明确区分单部件、公共组，以及产品确实需要时的分别变换。
2. 单部件模式只保存目标部件的变换基线，公共组模式保存整个组。选择集不应隐式代替目标集合。是否改变可见选择集由交互规则单独决定。
3. 能力检查覆盖整个目标集合。混合棱柱与方盒不能通过单部件入口进入未经定义的组 SCALE。若允许混合动作，明确每种目标的单位和结果，并让显示、命中与执行使用同一计划。
4. 控制器接收已经验证的计划，不再用 common 布尔值和任意 baseline 列表重新猜测语义。复用已有编辑 token、基线恢复和一次手势一个历史节点，不重写已验证的取消机制。
5. 验收覆盖 A 已选且 B 已选、Ctrl 追加后拖动、单部件与公共手柄、不同尺寸、不同旋转和混合棱柱。断言受影响 ID 集合、量化单位、中心、结果及取消恢复一致。
